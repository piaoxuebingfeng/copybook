### 为什么 v1 用「一行一个音节」而不是「一个方格一个音节」

方格方案有个硬约束：`zhuāng` 是 6 个字母，在 2.38cm 的方格里放不下。
硬塞就得缩小字号，而**字号一缩，x-height 就不再等于一条带**，字母立刻脱离四线格的带 ——
这正是本功能最难保证、也最容易被忽略的地方（见第三节）。

「一行一个音节」没有这个问题：音节有多长都放得下，字母永远按标准大小坐在带上，
这也是课本和市面字帖最常见的拼音练习格式。方案 C（一格一个字母）则在方格方案里
天然成立 —— 一个方格放一个字母，永远是放得下的。

### 公共层的边界

`sheet_layout.py` 只放**与「格子里画什么」无关**的东西，从 `generate_zitie.py` 机械抽取
（732 → 664 行）：

- 单位换算与行高量子化（`snap_up_pt`：所有行高必须是 0.75pt 的整数倍）
- 列宽 ↔ 像素标定（Excel/WPS 与 LibreOffice 公式不同）
- 页设置 / 打印区域 / 分页符 / 裁切线
- 单元格内贴图（`place_image` / `place_inset_image`）
- 2×2 子格画田字格（`box_borders`）
- 合并单元格文字宽度自检（合并会**直接裁字**，不报错不换行）

抽取过程有**零回归保证**，并且已经验证通过：重构前后重新生成 5 个产物
（纵向 / 横向 / 紧凑 / 笔顺 / 横向笔顺），**xlsx 逐 XML 条目一致、PDF 逐页像素一致**。

## 三、四线三格的几何（本功能的主要技术难点）

### 格子结构：3 个子行，不是 2 个

田字格用 **2×2 子单元格**画「外框 + 内部十字」。四线三格有 **3 条等分带**，
2 个子行表示不了 3 等分，所以：

```
田字格：  SUB_PX  = 45px  ->  CELL = 90px = 2.38125cm   （2 子行）
四线三格： SUB3_PX = 30px  ->  CELL = 90px = 2.38125cm   （3 子行，每带 30px）
```

**两条生成线的格子边长恰好相同（2.38125cm）**：整数像素里能同时被 2 和 3 整除的
最小值是 90。一行四线格总宽 8 个格 = 720px = 19.05cm，与汉字字帖的田字格总宽一致。

四线三格用**原生 Excel 边框**画：上下两条绿实线（外框），中间两条灰虚线（辅助线），
和汉字字帖的视觉语言一致（外实内虚）。

### 字母要「坐」在正确的带上

这是最容易做歪、也最容易被忽略的地方。三条带的分工是固定的：

| 带 | 内容 | 例 |
| --- | --- | --- |
| 上带 | 升部字母、声调符号 | `b d h k l`、`ā` 上的一横 |
| 中带 | x-height（字母主体） | `a o e m n` 的主体 |
| 下带 | 降部字母 | `g p q y` 的尾巴 |

所以**不能「把字放进格子居中」就完事**。做法：

1. **实测** `x` 的墨迹高度，反解字号使 x-height 恰好等于一条带（不信字体度量）
2. 用 `anchor="ms"`（水平居中 + 基线对齐）把**基线钉在框高的 2/3 处**

于是中带 = [1/3, 2/3] 正好是字母主体，升部/声调/降部自然伸进上下带。
另外贴图时**纵向必须零内缩**，高度必须**正好等于三行子行之和** —— 差 1px，
图里的带界就和 Excel 画的虚线错开，字母会整条带地偏，而且不报错。

实测结果（框高 90px）：`o`/`x` 墨迹落在 28~59（全在中带内），`b`/`l` 顶到 13（进上带），
`g`/`y` 底到 68（进下带），`ā`/`bā`/`mā` 顶到 19（声调进上带）。

## 四、字体策略

**实测结论**（本机 2026-10，用 fontTools 读 cmap 逐个字符验证）：

| 字体 | 许可 | 拼音字符（含第三声 `ǎěǐǒǔǚ`） |
| --- | --- | --- |
| 楷体 KaiTi / 微软雅黑 / 等线 | 私有，**不可分发** | 齐全 |
| **AR PL UKai**（楷体风格） | Arphic Public License，**可分发** | 齐全 |
| **Noto Serif / Sans CJK** | OFL，**可分发** | 齐全 |
| HarmonyOS Sans SC | 华为自有，分发条款不明确 | 齐全 |

注：第三声（`ǎ` U+01CE 等）是**中文老字体最容易缺的一组** —— 很多字体有
`á/à`（Latin-1）却没有 `ǎ`。所以这一项必须实测，不能凭印象。

设计：

1. 按优先级自动探测：`fonts/` 用户自备 → 楷体 → AR PL UKai → Noto CJK → …
2. **运行时校验覆盖**：缺哪个字符就明确报出来并中止，绝不默默渲染成豆腐块
3. 仓库**不内置任何字体**（私有字体有法律问题，开源字体动辄 20MB+）

## 五、输入格式

沿用汉字字帖「一行一组、`组名: 音节表`」的写法：

```
一组: bā 八 / mā 妈 / bà 爸 / mǎ 马
二组: xiǎo 小 / shàng 上 / xué 学 / lǎo 老 / shī 师
```

- 声调用**预组合字符**（`ā` `á` `ǎ` `à`），不要自己叠 —— 叠加的符号位置会漂，
  而且不同字体漂得不一样
- 也支持**数字标调**（键盘友好）：`ba1`→`bā`、`ma3`→`mǎ`、`ma5`→轻声、
  `nv3`→`nǚ`。标调位置按《汉语拼音方案》：`a o e` 优先，`iu/ui` 标后者，
  否则标在唯一的元音上
- 音节后可以跟一个汉字做标注：`bā 八`
- **非法音节会被拦下**（如 `ba9`）：不拦的话它会被原样渲染成一个带数字的音节
  贴进字帖 —— 不报错，但内容是错的

## 六、验收方式

**四道验收**，每道都能独立把「看着差不多但其实是错的」抓出来
（`python3 verify_pinyin.py 字帖.xlsx --chars="…" --pdf=字帖.pdf`）：

| # | 查什么 | 为什么必须查 |
| --- | --- | --- |
| 1 | **三带等高**：每个四线三格由 3 个等高的子行组成 | 四线三格的立身之本；用边框特征识别块，不认行号 |
| 2 | **贴图对齐**：锚点在三条带的第一行、纵向零偏移、高度正好等于三行之和 | 差 1px 字母整条带偏，且不报错 |
| 3 | **贴图内容**：把 xlsx 里嵌的图按**像素内容**反查是哪个音节，逐块比对 | 不看文件名，贴错图 / 渲染不一致都会被抓出来 |
| 4 | **PDF 真实像素**：两条虚虚线必须把上下绿实线严格三等分；印出来的墨迹范围必须和**渲染器为该音节生成的图**里的墨迹范围一致 | 端到端；对升部/降部/声调一律成立 |

第 4 条一开始我写的是「墨迹底部 ≈ 2/3（基线）」，结果把 `shàng` 判成了错的 ——
`g` 有降部，底部本来就该伸到下带。**判据本身错了，不是产物错了**：
换成「与渲染意图一致」后，对任何音节都成立。

> 与汉字那侧的五道验收（笔画数据 / 教学条像素 / 逐格排布 / PDF 几何 / 教学条宽度）互补。

## 七、模块划分

```
sheet_layout.py      共享版面层（两条生成线共用；汉字线已改为调用它，零回归已验证）
pinyin_input.py      音节表解析、数字标调转换、合法性校验（无词典、无多音字问题）
render_pinyin.py     字体探测 + 覆盖校验 + 按基线对齐的四线格渲染 + 批量 CLI（写 plan.json）
generate_pinyin.py   拼音排版：原生四线格边框 + 贴图 + 按块高分页
verify_pinyin.py     四道验收
zitie_gen.py         总入口：--type=pinyin（默认 hanzi，向后兼容）
```

汉字那侧的四个渲染模块（`render_strokes` / `render_trace` / `stroke_lib` /
`stroke_store`，共 838 行）**完全没有被改动**，它们继续只服务汉字笔顺。
